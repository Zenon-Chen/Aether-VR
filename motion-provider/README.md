# Aether Motion Provider

Standalone DART motion-generation sidecar. `mock` is deterministic test output and is used **only** when explicitly selected; every real backend requires a separate DART checkout/model assets via `DART_ROOT`.

## Install

Create the bundle venv and install this wheel/server dependencies first:

```powershell
py -m venv .venv
.\.venv\Scripts\python -m pip install --upgrade pip
.\.venv\Scripts\python -m pip install ".[server]"
```

Install the PyTorch build for the target vendor using the command generated by <https://pytorch.org/get-started/locally/>; do not rely on the package resolver to choose a GPU runtime. Examples (versions/index URLs change, so confirm upstream):

```text
# NVIDIA CUDA: select Windows/Linux + Pip + the installed CUDA option on pytorch.org
python -m pip install torch --index-url https://download.pytorch.org/whl/cu128
# AMD ROCm (Linux only): select Linux + Pip + the required ROCm option
python -m pip install torch --index-url https://download.pytorch.org/whl/rocm6.3
# Intel XPU: follow https://pytorch.org/docs/stable/notes/get_start_xpu.html
# CPU
python -m pip install torch --index-url https://download.pytorch.org/whl/cpu
```

Then install DART's actual dependencies from the external checkout:

```text
python -m pip install -r <DART_ROOT>/requirements_dart.txt
```

DART and model/checkpoint assets remain outside the wheel. Set `DART_ROOT`, and optionally `DART_CHECKPOINT` (otherwise the DART default checkpoint path is used). Native PyTorch ROCm is Linux-only here; Windows AMD is unsupported (no CUDA compatibility is claimed). Intel XPU is wired without CPU fallback, but DART deep-operator compatibility is experimental/unverified and must be validated on the target hardware.

`scripts/install.ps1` and `scripts/install.sh` install the provider/server and print the remaining vendor-runtime/DART steps.

## Diagnose / run

```text
motion-provider --diagnose --backend cpu
motion-provider --backend mock --generate "walk forward*2"
motion-provider --backend cuda --serve
```

`MOTION_PROVIDER_BACKEND=auto` chooses ROCm, NVIDIA CUDA, Intel XPU, then CPU; lack of `DART_ROOT` fails instead of generating mock output. Supported configuration variables include `MOTION_PROVIDER_DEVICE`, `MOTION_PROVIDER_DTYPE` (`float32` is currently required by DART), `MOTION_PROVIDER_HOST`, `MOTION_PROVIDER_PORT`, and `MOTION_PROVIDER_TOKEN`.

When `MOTION_PROVIDER_TOKEN` is set, all endpoints require `Authorization: Bearer <token>`, matching Aether Supervisor probes. Endpoints: `GET /health`, `GET /status`, `GET /capabilities`, `POST /generate`.

## Bundle

`bundle-manifest.json` is the Windows bundle template and uses Aether's `BundleManifest` fields plus Supervisor placeholders `{host}`, `{port}`, `{token}`, and `{bundle_dir}`. It intentionally does not override `DART_ROOT` or `DART_CHECKPOINT`: set those in the parent environment or add target-specific absolute paths when producing a release manifest. The Windows template targets `.venv/Scripts/motion-provider.exe`; Linux/ROCm packaging must emit a platform-specific manifest with `{bundle_dir}/.venv/bin/motion-provider`. A single manifest cannot be directly executable on both operating systems.
